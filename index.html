Reglas y Estándares de Arquitectura del CORE

Toda modificación, objeto PL/SQL, script DDL o interfaz gráfica en este repositorio debe respetar estrictamente estas 19 directrices vinculantes. El diseño garantiza alta escalabilidad, aislamiento multi-inquilino estricto, observabilidad en tiempo real y compatibilidad nativa con Oracle AI Database 23ai/26ai.

REGLA #1 ● Obligatoria

Skill Activa Obligatoria (oracle-plsql-architecture)

La skill oracle-plsql-architecture es vinculante e innegociable para cualquier desarrollo, modificación, revisión o propuesta de código PL/SQL en el repositorio.

Ubicación: .agents/skills/oracle-plsql-architecture/SKILL.md
Gobierno de desarrollo AI & Humano Innegociable
REGLA #2 ● Base de Datos

Prefijo de Tablas y Secuencias (core_*)

Todas las tablas del CORE deben iniciar obligatoriamente con el prefijo core_ (ej. core_tenant, core_usuario) y sus secuencias correspondientes con core_*_seq.

core_<tabla> & core_<tabla>_seq (START WITH 1 INCREMENT BY 1 NOCACHE)
Total: 37 tablas / 37 secuencias Estandarizado
REGLA #3 ● Nomenclatura Tablas

Nomenclatura Estricta en Singular para Tablas

Todo nombre de tabla debe definirse obligatoriamente en singular estricto en idioma español (ej. core_usuario, core_rol, core_permiso, core_proceso, core_archivo, core_notificacion, core_error). Queda terminantemente prohibido el plural (ej. core_usuarios, core_roles, core_notificaciones). Garantiza correspondencia natural 1:1 con las FKs (id_<entidad>), registros %ROWTYPE y DAOs (PKGCORE_<ENTIDAD>_DAO).

core_usuario, core_rol, core_proceso, core_archivo, core_error
FK: id_usuario, id_proceso | Registro: vro_core_usuario
Instancia individual de entidad Singular Estricto
REGLA #4 ● Clave Primaria

Llave Primaria Numérica por ID

Toda tabla debe tener como primer campo y llave primaria exclusiva el campo id de tipo NUMBER(12). En tablas multi-tenant, id_tenant se ubica como segundo campo referenciando a core_tenant(id).

PRIMARY KEY (id)
FOREIGN KEY (id_tenant) REFERENCES core_tenant(id)
Identificador único numérico Obligatorio
REGLA #5 ● Nomenclatura FK

Claves Foráneas con Prefijo id_

Toda columna que haga referencia al id de otra tabla debe comenzar obligatoriamente con el prefijo id_ seguido del nombre de la entidad referenciada en singular (ej. id_persona, id_usuario, id_rol, id_proceso, id_objeto).

id_persona -> core_persona(id)
id_usuario -> core_usuario(id)
id_rol -> core_rol(id)
Consistencia referencial 100% id_<entidad>
REGLA #6 ● Documentación

Documentación Obligatoria en Diccionario de Datos

Todo script DDL debe contener obligatoriamente la documentación técnica mediante sentencias Oracle COMMENT ON TABLE para la descripción de la entidad y COMMENT ON COLUMN para cada una de las columnas de la tabla.

COMMENT ON TABLE core_usuario IS '...';
COMMENT ON COLUMN core_usuario.correo_electronico IS '...';
Diccionario en base de datos 100% Columnas
REGLA #7 ● Capa DAO

Nomenclatura DAO Oficial y 20 Métodos

Fórmula exacta: PKG<TABLA>_DAO (ej. PKGCORE_USUARIO_DAO). Implementa la suite oficial de 20 métodos estándar incluyendo f_total_paginas (recibe JSON con "registros" y retorna total de páginas) y f_consultar_paginado (recibe página y registros y devuelve JSON paginado). En tablas multi-tenant, id_tenant es parámetro opcional (DEFAULT NULL). Prohibido ejecutar COMMIT o ROLLBACK dentro de paquetes DAO.

v_paginas := PKGCORE_USUARIO_DAO.f_total_paginas('{"registros":10}');
v_json := PKGCORE_USUARIO_DAO.f_consultar_paginado(p_pagina => 1, p_registros => 10);
Sin COMMIT espurio Plantilla 20 Métodos
REGLA #8 ● Tipos de Dato

Banderas y Booleanos NUMBER(1) con CHECK

Todo campo que represente valores lógicos, activos o booleanos (0 o 1) debe definirse obligatoriamente como tipo numérico NUMBER(1) con valores por defecto 1 o 0 y restricción CHECK (<columna> IN (0, 1)). Prohibido usar CHAR(1) o texto.

es_activo NUMBER(1) DEFAULT 1 CHECK (es_activo IN (0, 1))
Prohibido CHAR(1) NUMBER(1) IN (0, 1)
REGLA #9 ● Nomenclatura

Columnas en Español (Conservando tenant y oidc)

Todos los nombres de columnas deben estar redactados en idioma español (ej. nombre_usuario, correo_electronico, primer_ingreso, ultimo_ingreso, id_traza, hash_token), conservando los términos institucionales tenant y oidc.

id_tenant, oidc_sub, oidc_proveedor, estado_registro, direccion_ip
Español técnico Estándar
REGLA #10 ● Triggers

Triggers Before-Insert de Autonumeración (TRG_BI_*)

Toda tabla con clave primaria basada en secuencia debe implementar su trigger BEFORE INSERT con la nomenclatura oficial TRG_BI_<TABLA> (ej. TRG_BI_CORE_USUARIO). Si el :new.id IS NULL, asigna el NEXTVAL de la secuencia.

IF :new.id IS NULL THEN
  :new.id := core_<tabla>_seq.NEXTVAL;
END IF;

Prefijos Estrictos de Subprogramas y Variables

Procedimientos: p_. Funciones: f_. Variables locales: v_ (escalares), vro_ (registros %ROWTYPE), vta_ (colecciones). Parámetros formales: p_ (escalares), pro_ (registros), pta_ (colecciones).

REGLA #12 ● Orquestadores

Orquestadores Frontend (pkgln_) con Firma CLOB

Todo subprograma expuesto para consumo del Frontend o APIs reside obligatoriamente en pkgln_ con firma fija de 2 CLOBs: p_json_entrada (IN CLOB) y p_json_salida (OUT CLOB). Se prohíbe la concatenación manual de cadenas; se usa SQL/JSON nativo.

PROCEDURE p_operacion (
  p_json_entrada IN CLOB,
  p_json_salida OUT CLOB
);
Firma estandarizada p_json_entrada/salida
REGLA #13 ● Observabilidad

Gestión Centralizada de Trazabilidad (uti_manejo_trazas_pkg)

Todo orquestador pkgln_ debe delegar el ciclo de vida de telemetría en uti_manejo_trazas_pkg. Primero verifica con f_debe_trazar contra core_traza_config; si aplica, apertura con p_iniciar_traza, cierra con p_finalizar_traza al éxito (tras commit) o con p_finalizar_traza_error ante excepciones (tras rollback).

uti_manejo_trazas_pkg (f_debe_trazar, p_iniciar_traza, p_finalizar_traza)
Telemetría autónoma y segura uti_manejo_trazas_pkg
REGLA #14 ● Transacciones

Commit Centralizado y Controlado (p_do_commit)

Queda terminantemente prohibido ejecutar COMMIT; directo. Toda confirmación se ejecuta exclusivamente en el orquestador pkgln_ invocando p_do_commit('<paquete>.<metodo>');. En fallo en WHEN OTHERS, se ejecuta ROLLBACK; antes de persistir el error en core_error con uti_ge_excepciones_pkg.p_grabar_log.

p_do_commit('pkgln_usuarios.p_crear_usuario');
EXCEPTION WHEN OTHERS THEN ROLLBACK; ...
Transacciones atómicas p_do_commit
REGLA #15 ● DML Multi-Tabla

Paquetes Multi-Tabla y JSON_TABLE (pkgcn_)

Los paquetes pkgcn_ tienen como responsabilidad exclusiva ejecutar sentencias DML que afecten a más de una tabla de manera coordinada y desestructurar payloads JSON complejos usando la sintaxis nativa SQL JSON_TABLE. No ejecutan commit.

JSON_TABLE(p_json_entrada, '$.detalles[*]' COLUMNS (...))
Sin control transaccional pkgcn_

REGLA #18 ● Multi-Tenancy

Aislamiento por Application Context (Enfoque B - DML Blindado)

Toda sentencia DML en tablas multi-tenant aplica obligatoriamente el Enfoque B con SYS_CONTEXT('CORE_CTX', 'ID_TENANT'): en SELECT/UPDATE/DELETE filtra con WHERE id_tenant = NVL(p_id_tenant, TO_NUMBER(SYS_CONTEXT('CORE_CTX', 'ID_TENANT'))), y en p_insertar asegura el tenant antes de insertar. En paquetes _DAO y PKGCA_, id_tenant es parámetro opcional (DEFAULT NULL).

WHERE id_tenant = NVL(p_id_tenant, TO_NUMBER(SYS_CONTEXT('CORE_CTX', 'ID_TENANT')));
vro.id_tenant := NVL(vro.id_tenant, TO_NUMBER(SYS_CONTEXT('CORE_CTX', 'ID_TENANT')));
Enfoque B - DML Blindado Enfoque B / CORE_CTX
REGLA #19 ● Sintaxis SQL

Prohibición de Nomenclatura JOIN (Sintaxis Tradicional Oracle)

En toda sentencia SELECT y consulta SQL queda terminantemente prohibido el uso de la nomenclatura ANSI JOIN (INNER JOIN, LEFT JOIN, etc.). Todas las consultas multitabla deben estructurarse con la sintaxis tradicional de Oracle: tablas separadas por coma en la cláusula FROM, condiciones de enlace en el WHERE, y uniones externas exclusivamente mediante el operador nativo (+).

FROM core_usuario u, core_persona p
WHERE p.id(+) = u.id_persona
  AND u.id_tenant = NVL(p_id_tenant, TO_NUMBER(SYS_CONTEXT('CORE_CTX', 'ID_TENANT')));
Sin ANSI JOIN Sintaxis Tradicional (+)
